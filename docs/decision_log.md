# TAC Decision Log

Maintained per [Development_Protocol.txt](Development_Protocol.txt) Section 2. This log records *why* material decisions were made and how they evolved. It describes history, not current state: current state lives in [project_ledger.md](project_ledger.md). Append to it as decisions are made; do not reconstruct it from memory.

## How an entry works

- Entry IDs are `DL-NNN`, numbered in order and never reused. Each entry starts from a story: the observed behavior or problem and what is actually known, before any solution.
- Each entry has these labeled blocks. Approving a name or a number is not approving a requirement; do not let approval of one block imply approval of another.
  - **Status:** confirmed, provisional, or dependent on an open question, with the date.
  - **Requirement:** behavior explicitly stated or approved by the developer.
  - **Design choices:** the shape of the solution, agreed with the developer.
  - **Implementation choices:** details left to Claude.
  - **Open:** unresolved questions, and a list of what is **not yet verified** and must not be described as confirmed. Update that list as items are resolved.
  - **Shares a seam with:** other entries touching the same hook point, data or ordering constraint, written when the entry is made.
  - **Supersedes:** the earlier decision or spec item this changes, if any.
  - **Source:** the evidence, requirement or constraint that drove it.
- The log is append-only. Never rewrite an entry; add a dated **Addendum** under it so the correction and the original reasoning are both visible.
- Work done outside the main repository or session still gets an entry (a retrofit entry if found later, Protocol §19).

### DL-002 — TAC logs move to `Logs\TAC\`

- **Status:** In progress, 2026-10-13. Requirement agreed in conversation; design not yet agreed; nothing built. This entry lives on branch `feat/log-folder` until the feature merges.
- **Story:** the Protocol (§8) puts a script's logs in a folder named for the script under the MacroQuest `Logs` folder. ### DL-003 — Priority ordering for `onCommand` and `onBetweenPulls`

- **Status:** In progress, 2026-10-13. Requirement confirmed; design open; nothing built. This entry lives on branch `feat/hook-priority` until the feature merges.
- **Story:** the plugin manager (`pm.dispatch` in `TAC/lua/triune.lua`) runs the first-handled hooks `onCommand` and `onBetweenPulls` in load order (`pm.pluginOrder`) and stops at the first truthy answer. `docs/HOOKS.md` section 3.2 already decides that these two are ordered by an explicit `priority` instead, with an alphabetical tie rule, and lists the name, range and documentation of the field as still open (section 9). Known from the code: only `auto_aa` implements `onBetweenPulls`; about 20 plugins implement `onCommand`. Not checked: whether any two shipped plugins claim the same command.
- **Requirement:**

  2. (Developer, 2026-10-13, in their own words.) This is groundwork for plugin authors and is a requirement. The developer has not seen two plugins conflict. It is built without an observed failure, on the developer's decision.
- **Design choices:** none agreed yet.
- **Implementation choices:** none.
- **Open:** the name and place of the field and its range (HOOKS.md section 9, "Still open"); how it is documented for plugin authors; whether `core.hasCapability` advertises it (not asked for, not decided); behaviour for a missing or non-numeric value; how a changed priority takes effect on reload; whether any shipped plugins claim the same command today. **Addendum to DL-003, 2026-10-13 — design choice 1 approved (HANDOFF Step 1 / Decision 1 / Revision 0; REVIEW OF the same, ChatGPT, 2026-10-13; developer's approval: "I approve as reached by consensus.").**
- **Decision:** a plugin declares its priority as a number field named `priority` on the table its file returns. Core reads it when it loads the plugin (like `tickInterval`); a missing value means 0. There is no runtime setter.
- **Why:** it follows the existing plugin format, needs no new API entry, and nothing requires changing the value while running. The name stays `priority`, as in `docs/HOOKS.md` section 3.2. The core already uses `priority` for action settings (1 to 99, lowest first, `table.sort` with `<`), which is the opposite direction to the plugin field (highest first); the reviewer's view, which Claude accepted, is that they belong to different objects, so the name is kept and the difference is handled in the documentation.
- **Consequence recorded as a requirement on the documentation:** the plugin documentation must carry a worked example of two plugins with different priorities and the order they run in, and must say that action priorities run lowest first.
- **Correction accepted from the review:** the earlier wording "nothing breaks" was too broad. What is established: changing a plugin's declared value does not affect an already-loaded plugin immediately. Whether a reload applies it is a separate, undecided item.
- **Not decided here (each its own decision):** range and invalid values; whether `core.hasCapability` advertises the feature; how a changed value takes effect on reload; how the sorted order is kept; the documentation text. Nothing built.

**Addendum to DL-003, 2026-10-13 — design choice 2 approved (HANDOFF Step 1 / Decision 2 / Revision 0; REVIEW OF the same, ChatGPT, 2026-10-13; developer's approval: "I approve as reached by consensus.").**
- **Decision:** a valid `priority` is a finite Lua number, negatives and fractions allowed, no range limit. A missing value is 0 with no warning. A present but invalid value (a string including a numeric string such as `'10'`, a table, a boolean, NaN, or an infinity) counts as 0, the plugin still loads, and one warning line is written to the TAC log for that plugin each time it loads.
- **Why:** an author's mistake is visible instead of silent; no demonstrated need for a range limit; numeric strings are rejected so the field has one rule (it is declared as a number) and does not copy the `tonumber` conversion `tickInterval` happens to use.
- **Evidence and its limits:** run in LuaJIT on 2026-10-13: `tonumber('10')` is 10, `tonumber('0x10')` is 16, `tonumber('nan')` is NaN, `tonumber('inf')` and `tonumber('1e999')` are infinity. One sample sort with NaN priorities finished without error; it does not show NaN is safe. Reasoning, not verified: NaN breaks the comparison rules a sort relies on. Infinities can be ordered; rejecting them keeps the documented contract plainly finite (correction accepted from the review).
- **Not decided here:** whether `core.hasCapability` advertises it, reload behaviour, how the order is kept, the documentation text. Nothing built.

**Addendum to DL-003, 2026-10-13 — design choice 3 approved (HANDOFF Step 1 / Decision 3 / Revision 0; REVIEW OF the same, ChatGPT, 2026-10-13; developer's approval: "I approve as reached by consensus.").**
- **Decision:** the order is built at dispatch time, with nothing stored between calls. For `onCommand` and `onBetweenPulls` only, `dispatch` takes the plugins that are enabled, not in `Error`, define the hook and have not had that hook switched off, sorts them by `priority` (highest first) then plugin id (alphabetical), and stops at the first truthy answer. `wantsCombatHold` and all other hooks keep load order.
- **Reload consequence, approved as part of this decision:** a changed `priority` takes effect when the plugin's file is reloaded (the Reload button, or reload-all), because `pm.loadPlugin` re-reads it. A plugin already loaded keeps its old value, and `pm.restartAll` does not re-read files.
- **Why:** nothing to go stale, no cache invalidation points across `loadPlugin`, `reloadPlugin`, `reloadAll`, enable and disable.
- **Evidence and its limits (run 2026-10-13, LuaJIT, this machine, 100,000 calls each):** copy-and-sort of 1, 5, 20 and 25 implementers took 0.12, 0.62, 3.84 and 5.08 microseconds per call. This measures sorting only, not total runtime impact; the puller's call rate is **not measured**. If the call rate ever mattered, a cache would be a separate decision.
- **Not decided here:** whether `core.hasCapability` advertises the feature; the documentation text. Nothing built.

**Addendum to DL-003, 2026-10-13 — design choice 4 approved (HANDOFF Step 1 / Decision 4 / Revision 0; REVIEW OF the same, ChatGPT, 2026-10-13; developer's approval: "I approve as reached by consensus.").**
- **Decision:** core advertises the feature through the existing capability check. A manifest entry `hookPriority` (kind `value`, tier `experimental`, since `1.0`) and a core API value `core.hookPriority = true`, so a plugin can test `core.hasCapability and core.hasCapability('hookPriority')` when it starts and choose its own fallback.
- **Why:** it serves the confirmed purpose (groundwork for plugin authors): without it a plugin cannot tell support from a silent fallback to load order. It uses the established mechanism (`docs/HOOKS.md` 2.4 DECIDED: one check, no `hasHook`). `main` (gennro's V3.2) has no `hasCapability`, so a plugin must also handle it being `nil`.
- **Recorded as extra scope:** this is beyond the ordering itself (Protocol §3). It is justified only by the developer's stated purpose; no plugin author has needed it yet. The name keeps the capability (`hookPriority`) apart from the declaration (`priority`).
